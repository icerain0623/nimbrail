# Catalogue — OWASP Top 10:2025

版: **OWASP Top 10:2025**。2026-08-28 に owasp.org/Top10/2025/ と同 0x00_2025-Introduction
から取得。2021 と 2017 は同サイトが superseded として提示している。

出力にはこの版名をそのまま書く。番号は版をまたいで安定しないので、版名のない
「A01」は照合先を名乗っていない主張になる。2025 で動いた主なもの:

- SSRF は独立カテゴリではなく A01 に統合された（2021 では A10）。
- Vulnerable and Outdated Components（2021 A06）は A03 に吸収された。
- A07 は Identification and Authentication Failures から改称。
- A09 は Alerting が題に入った — 記録だけでは足りない。
- A10 は新設。

各カテゴリの「表面」「probe」「強制の証拠」「数えないもの」は OWASP の文言ではなく
このキット側の作業定義で、セルを埋める手順として書いてある。カテゴリ名と番号だけが
出典由来。より細かい検査項目が要るときは ASVS L1 が下位の網で、ここには畳んでいない。

版が変わったら差し替えるのはこのファイルだけで、SKILL.md の手順は版に依存しない。

## A01:2025 — Broken Access Control

- 表面: エントリポイント全件、所有者カラム、ロール集合、そして外向きリクエスト（SSRF はここ）。
- probe: 各エントリポイントについて認可判断が「どの行で」起きるかを 1 件ずつ引く。ルータ定義に
  並ぶ guard 名ではなく、その guard が登録されている箇所まで辿る。URL がユーザ由来の
  外向きリクエストを別に列挙する。
- 強制の証拠: 既定拒否（allowlist 側に足す構造）か、全エントリポイントを覆う 1 箇所。
  リソース取得に所有者条件が入っていること。
- 多テナント: 所有者条件の実体はテナント列で、ここが最も代償の大きいセル。ユーザ単位の
  所有者チェックが通っていても、テナント跨ぎが空いていることがある。
- DB 側: 行レベル認可はアプリコードとは別系統。RLS が無効なら全テーブルが素通しで、
  有効でもサーバ側が service role 相当の鍵で接続していれば迂回される。ORM 単体は
  行レベル認可を提供しない。
- 数えない: 認証と認可の混同（ログイン済みチェックは A01 の対策ではない）。ID が UUID
  だから安全という論法。クライアント側のロール分岐。

## A02:2025 — Security Misconfiguration

- 表面: Cookie 属性、CORS、セキュリティヘッダ、TLS 終端、デバッグ出力、既定資格情報、
  クラウド／IaC の公開設定、エラーページの詳細度。
- probe: 設定は「書かれていない」ことが所見になるので、有無を 1 項目ずつ確認する
  （Content-Security-Policy、Strict-Transport-Security、httpOnly と secure と sameSite、
  CORS の origin が反射でないか、本番でスタックトレースが出ないか）。
- 強制の証拠: 本番ビルドの経路に入っている設定。ローカル専用の分岐で囲われていないこと。
- 数えない: ミドルウェアが定義されているだけで mount されていないもの。プラットフォーム
  側（CDN、リバースプロキシ）が付けている可能性を確認せずに「ある」とみなすこと。

## A03:2025 — Software Supply Chain Failures

- 表面: マニフェストとロックファイル、install スクリプト、CI ワークフローとその権限、
  ベースイメージ、外部からダウンロードして実行しているもの、ビルド時に注入される値。
- probe: 監査コマンドをロックファイルの版で走らせる（pnpm audit、npm audit、pip-audit）。
  ロックファイルの存在と追跡状態。CI が third-party action を可変タグで参照していないか。
- 強制の証拠: ロックファイルが追跡されていること、監査が CI に入っていること、依存の
  追加に人のレビューが挟まること。
- 数えない: 脆弱性件数ゼロを対策ありとみなすこと — これは今日の状態で、経路の有無とは別。
  2021 の Vulnerable and Outdated Components はここに畳まれているので、CVE だけ見て
  供給網を見たことにしない。

## A04:2025 — Cryptographic Failures

- 表面: パスワードのハッシュ、トークン生成、保存時暗号化、鍵の置き場所、TLS 設定、
  署名検証。
- probe: ハッシュ関数とそのパラメータを呼び出し箇所から引く。乱数が暗号論的かどうか
  （Math.random、random.random が資格情報やトークンに使われていないか）。鍵が環境変数か、
  リポジトリ内か。
- 強制の証拠: 用途に合ったアルゴリズムの呼び出し箇所。鍵がコードの外にあること。
- 数えない: 暗号ライブラリが依存にあること。「HTTPS だから保存時も安全」という飛躍。

## A05:2025 — Injection

- 表面: 生クエリ、ORM の escape hatch、シェル実行、テンプレート出力、innerHTML 系代入、
  eval、ユーザ入力を含むパス結合とファイル読み出し、LDAP や NoSQL のクエリ組み立て。
- probe: シンクごとに grep して、ヒットの入力元を辿る。0 件ならパターンを出力に書く。
- 強制の証拠: パラメータ化された呼び出し。フレームワークの既定エスケープ（Django ORM、
  ERB、React の children）は実在の対策として引用し、opt out した箇所だけ見る。
- 数えない: 入力検証があるからシンクが安全という論法。到達経路を示せない指摘（未確認へ）。

## A06:2025 — Insecure Design

- 表面: 認証・決済・権限昇格・データ削除など、失敗の代償が大きいフロー。多段処理の
  途中状態。レート制限と乱用防止。
- probe: コードだけでは判定できない。仕様（SPEC.md / petrichor plan）の 業務フロー と
  権限マトリクス と突き合わせ、設計上の穴は `squall` へ、仕様と実装の食い違いは
  `weathering` へ回す。仕様が無ければ 未確認 とし、`overcast` を提案する。
- 強制の証拠: そのフローの設計判断がどこかに書かれていること。
- 数えない: 実装が動いていることを設計の妥当性の証拠にすること。

## A07:2025 — Authentication Failures

- 表面: ログイン、セッション発行と失効、パスワードリセット、多要素、招待とメール確認、
  トークンの寿命、ログアウト、アカウントロック。
- probe: セッションが「どこで」無効化されるかを引く（パスワード変更時、ログアウト時、
  権限変更時）。リセットトークンの寿命と再利用可否。列挙耐性（存在しないユーザと
  誤ったパスワードで応答が変わらないか）。
- 強制の証拠: 失効の呼び出し箇所。トークン寿命の設定値。
- 数えない: 認証ライブラリの採用そのもの。既定設定を確認せずに「ライブラリ任せ」とすること。

## A08:2025 — Software or Data Integrity Failures

- 表面: デシリアライズ、アップロードされたファイルの取り回し、自動更新や外部から
  取得したコードの実行、Webhook の受け口、信頼境界をまたぐデータ。
- probe: デシリアライズ呼び出しの入力元。アップロードのファイル種別判定が拡張子か
  マジックバイトか。Webhook の署名検証がハンドラの先頭にあるか。
- 強制の証拠: 署名または整合性検証の呼び出し箇所が、データを使う前にあること。
- 数えない: 検証関数の存在。呼ばれる位置が使用後なら対策ではない。

## A09:2025 — Security Logging and Alerting Failures

- 表面: 認証の成否、認可拒否、権限変更、データ削除、管理操作の記録。ログの保存先と
  保持期間。そして通知経路。
- probe: 上記イベントごとに記録箇所を引く。ログに資格情報や個人情報が落ちていないか
  （ここで見つかったものは `private-scan` の担当ではなく実行時の漏洩）。異常が人に
  届く経路があるか。
- 強制の証拠: 記録の呼び出し箇所と、閾値を超えたときに通知が飛ぶ設定。
- 数えない: ログが出ていることを対策ありとみなすこと。2025 は Alerting を題に入れて
  いるので、誰にも届かないログは 不在 に寄る。

## A10:2025 — Mishandling of Exceptional Conditions

- 表面: 例外処理、認可や検証の失敗経路、外部依存のタイムアウトと縮退、トランザクション
  の巻き戻し、リトライ。
- probe: 認可・検証・署名検証の各判定について、例外時にどちらへ倒れるかを読む。握り潰し
  （空の catch、ログだけして続行）を grep する。外部呼び出しの失敗時に処理が続くか。
- 強制の証拠: 失敗時に拒否側へ倒れていることが読める分岐。
- 数えない: try が書かれていること。例外が出ないことを設計上の保証とみなすこと。
